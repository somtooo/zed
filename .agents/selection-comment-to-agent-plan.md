# Selection Comment to Agent — Product and Implementation Plan (v2)

Branch: `selection-comment-to-agent`, forked from `agent-response-scroll-position-v2`. This fork will not merge upstream. Correctness comes first, upstream resilience second. Where the two conflict, choose correctness and isolate the diff so a future rebase stays mechanical.

Intent: Delta style review capture. The user selects code in any editor or review diff, writes a note in place, repeats across files, and sends once from the agent panel. The agent draft is the queue. Inline blocks are the visible record of what has been queued.

Out of scope: hosted pull request posting, durable comment storage across restarts, automatic submit. If the editor closes or the app restarts before send, unconfirmed inputs are lost and confirmed markers are best effort. The draft in the agent panel is the source of truth once queued.

## Product intent

This is a batching tool for review feedback. Without it the reviewer must shuttle between code and chat, quoting one range, typing one note, sending, repeating. With it the reviewer stays in the code, leaves a trail of small notes exactly where the problem is, and sends one coherent message. The inline blocks therefore serve two jobs. Before confirm they are an input. After confirm they are a marker that says a comment lives here and has already been queued. That second job is why confirm must not close the block. If the block vanished on confirm, the user would have no way to see at a glance which selections already have feedback, and would double comment or miss spots.

## User journey

Entry is available in all three places at once: the editor context menu alongside Add to Agent Thread, the command palette as Add Selection Comment To Thread, and a default keybinding. All three invoke the same action. There is no mode where only one of them works.

If the selection is nonempty, we use it. If it is empty, we expand to the full line under the cursor, following the existing Add Selection To Thread convention. This defines the empty selection case out of existence instead of showing an error. Multiline and single line selections both work. Cross buffer selections in a multibuffer use the same range resolution the agent already uses, and if no resolvable range exists the action does nothing.

On invoke, a new unconfirmed block appears below the end of the selection, anchored to a stable multibuffer anchor so it tracks edits and scrolling. Focus moves into its input. The source selection highlight stays visible. Multiple unconfirmed and confirmed blocks can coexist in one editor and across editors. Invoking again with a different selection creates another block rather than replacing the first. This is the largest departure from the single pending input pattern, and it is deliberate. A review with one slot is not a review tool.

An unconfirmed block is an editor. It shows placeholder text Comment on selection, accepts typing and paste, grows from one line to a small maximum with internal scroll, and uses the standard elevated surface container with anchor aligned padding so it looks native in every theme. Cmd Enter and Ctrl Enter on Linux confirm. Enter alone inserts a newline once multiline is enabled. Esc cancels that block only, removes it, and restores focus to the source editor. Changing the source selection does not destroy other blocks. Closing the buffer destroys its blocks. Confirm with empty or whitespace only text does nothing and leaves the block open, so there is no empty comment state to handle downstream.

On confirm, two things happen atomically from the user perspective. The selection plus the written comment are appended to the active agent thread draft as a file pill with line range followed by prose, identical in appearance to Add Selection To Thread output. And the block transitions in place from unconfirmed to confirmed. It does not close. It changes visually to a read only marker showing the comment text, with a distinct treatment from the input state. Focus returns to the source editor so the reviewer can immediately make the next selection. The agent panel is not force focused on each confirm. Quiet accumulation is the point. A subtle count of queued comments can appear later, but forced focus switching would break the review loop.

A confirmed block is a marker, not a second input. It uses a muted read only row with a left accent and a confirmed affordance such as a check icon, clearly distinct from the focused input border of the unconfirmed state. It shows the comment text truncated with full text on hover or expand. It offers edit and delete on hover. Edit returns it to the unconfirmed input state with the prior text restored, without duplicating the queued draft entry until reconfirmed. Reconfirm appends an updated entry, which is acceptable for this fork because the draft remains user editable and the send is the commit point. Delete removes the marker only and leaves the already queued draft text alone, again because the draft is the source of truth and the user can trim it before sending. This keeps the state model honest: markers record where feedback was left, the draft records what will be sent.

Sending from the agent panel clears all markers. When the user sends the thread message to the model, every confirmed and unconfirmed selection comment block in every editor is removed. This is the close condition. It gives the exact guarantee the reviewer needs: if a marker is on screen, its content is still unsent. If the screen is clean, everything went. Failed or cancelled sends do not clear. Only a successful send to the model clears. If the user clears the agent draft manually without sending, markers stay, which is correct because nothing was sent.

## Visual and interaction contract

Both states reuse theme tokens exclusively, so light and dark themes and mid session theme switches require no code. The unconfirmed state reuses the inline input construction: nested editor through EditorElement inside a container with elevated surface background, subtle border, standard radius, and anchor aligned left padding. The confirmed state reuses the same container geometry but swaps the editable field for a read only row with muted text color, accent border, and small icon actions. No hardcoded colors, no custom shadows, no new typography. The box is beautiful because it is indistinguishable from the rest of Zed.

Keyboard and focus behavior is fixed. Invoke focuses the new input. Esc in an unconfirmed input removes only that input. Esc elsewhere follows the existing dismiss menus and popups path and must not wipe confirmed markers. Cmd Enter confirms from inside the input. Tab moves within the input normally. After confirm, focus returns to the source editor at the prior selection head so keyboard driven review keeps flowing. Mouse behavior follows the existing block convention: interacting with the block does not corrupt the source selection, and scrolling keeps blocks anchored below their ranges.

## Technical shape

This needs a real multi block store, not the single pending input. The single pending input supports one block, cancels on selection change, and is removed on confirm, which is the opposite of the required semantics. The correct precedent is the diff review overlay collection, which keeps a vector of overlays with block ids, anchor ranges, prompt editors, and expanded state, rendered through generic block properties below an anchor. The new module follows that shape but is decoupled from diff hunks. Its key is a stable anchor range plus a monotonically increasing local id, never a hunk key, so it works identically in normal editors and in diff multibuffer right hand editors.

The module boundary is drawn for dependency direction. The editor crate owns placement, storage, rendering, and focus. It knows nothing about the agent. It exposes a narrow public surface: show a comment input for a selection, confirm or cancel one block, edit or delete a confirmed block, clear all blocks in an editor, and enumerate confirmed comments. The agent crate owns queuing. It calls show with callbacks, and on confirm it reads the selection through the existing AgentContextSource path, inserts the selection pill through the existing insert selection path, and appends prose through the existing insert text path. No mention creation logic is duplicated. No new mention type is introduced. MentionUri Selection is reused verbatim.

Naming follows the neighborhood so a future reader guesses correctly. SelectionComment for the stored record with range anchors, snapshot text, comment text, and confirmed flag. SelectionCommentOverlay for the live block binding block id to record id. show selection comment input, confirm selection comment, cancel selection comment, clear selection comments, AddSelectionCommentToThread for the action. Tests follow the existing editor test and conversation view test shapes: show on selection, Esc removes only the target, confirm keeps a confirmed marker and appends one pill plus prose, empty confirm is a no op, second invoke creates a second block, send clears all.

The send to clear wiring is explicit. The agent send path calls into a small clear hook after a successful send dispatch. Editors do not poll. The hook iterates open editors and calls the public clear. The exact send commit point must be verified against ThreadView send implementation and MessageQueue behavior during generation, because follow ups typed while generating take a different queue path. The rule stays simple regardless of path: markers clear only when content actually leaves to the model, never on draft edit, never on focus change, never on theme change.

## File plan

New files, which justify themselves as new logical components. `crates/editor/src/selection_comments.rs` owns the record vector, block lifecycle, render functions for both states, height management, and focus restore. `crates/agent_ui/src/selection_comment.rs` owns the action handler, the confirm closure that bridges editor selection to agent draft, and the post send clear hook helper.

Minimal touches elsewhere, additive only. One action definition beside AddSelectionToThread in `crates/zed_actions/src/lib.rs`. One module declaration for each new file. One registration for the new action beside the existing AddSelectionToThread registration in `crates/agent_ui/src/agent_panel.rs`. One context menu entry beside Add to Agent Thread in `crates/editor/src/mouse_context_menu.rs`. One default keybinding entry plus palette availability, which actions get for free. One narrow visibility widening or thin public wrapper so the agent crate can show the editor input without reaching into privates. One hook call on the verified send commit path to clear markers. No renames. No signature changes to hot functions. No new fields scattered through Editor; overlay state lives in the new module keyed by editor.

Upstream resilience without sacrificing correctness means keeping every touch small and obvious, not avoiding necessary touches. The new files carry the complexity. The touched files each gain a few lines that are trivial to reapply if upstream refactors them. A single feature flag gates entry points so rebases stay buildable with the feature off. Weekly rebase discipline is to rebase, run the focused editor and agent_ui tests, and adapt only the thin call sites.

## Testing and definition of done

Editor level tests cover show on nonempty selection, empty selection expands to line, Esc cancels only the focused unconfirmed block, confirm preserves a confirmed marker with distinct state, empty confirm leaves the input open and queues nothing, multiple blocks coexist, anchor shift on edit keeps blocks attached, buffer close drops its blocks. Agent level tests cover confirm appends one selection pill plus prose in order for two sequential comments, manual draft edits do not disturb markers, and successful send clears all markers across editors while cancelled send keeps them. Manual verification covers normal buffer and review diff, light and dark themes, multiline growth, focus return for rapid successive comments, and the three entry points working identically.
